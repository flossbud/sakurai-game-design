[00:04](https://youtu.be/mQJEWMmZutA?t=4) A system for bug testing, or finding and stamping out bugs in the code, is a requirement for every game.

[00:14](https://youtu.be/mQJEWMmZutA?t=14) Usually, only a small handful of bugs will show up in a game's release version, but before reaching that point, countless bugs have to first be fixed. Handing playtesting duties to team members who can fix bugs—especially programmers— results in a lot of lost time, which is why just about every project will have a team of bug testers to find any potential issues.

[00:36](https://youtu.be/mQJEWMmZutA?t=36) Some companies even specialize in bug testing. For those struggling to imagine how this works, I'd like to explain the basics of the bug testing process. To start, as a fundamental rule, we have to make sure that everyone is using the latest daily build of the game.

[00:54](https://youtu.be/mQJEWMmZutA?t=54) Bugs found on the wrong version aren't helpful, and can cause problems. First, bug testers playtest the game. They don't just aimlessly play, but go through design documents to test all sorts of combinations, or split into subteams that each check a specific part of the game to make sure nothing gets missed.

[01:15](https://youtu.be/mQJEWMmZutA?t=75) They'll make checklists, too. Once someone finds a bug and figures out how to reproduce it, they'll report the bug as a ticket. A ticket is essentially a task you write and track online. Managing these tasks and assigning them properly decreases the chance of things being overlooked.

[01:35](https://youtu.be/mQJEWMmZutA?t=95) Based on the severity of a bug, the manager will assign it a class. Class S is for bugs that cause hangs or can potentially corrupt save data. Class A is for bugs that prevent players from progressing in the game. Lower-class bugs are sometimes waived, or intentionally left alone.

[01:55](https://youtu.be/mQJEWMmZutA?t=115) Along with the class, the manager also decides which subteam or team member to assign the bug to. Programmers aren't always the right people to fix bugs, ater all. Character problems get fixed by an artist, while broken animations get fixed by an animator. Once a fix is implemented, the ticket is sent back to the bug tester.

[02:17](https://youtu.be/mQJEWMmZutA?t=137) Once the fix has been confirmed in a variety of configurations, the task is finished. However, the ticket isn't simply discarded, but changed to “resolved” status in case the bug ever reoccurs. By passing tickets between relevant team members, the issues won't sit around, and should always end up getting resolved.

[02:40](https://youtu.be/mQJEWMmZutA?t=160) When two bugs are related, their tickets might end up cross-referenced or merged. And if a team member is assigned too many tickets, others may take some bugs to help them out. Visualizing tasks is vital in this process. Bug testing tends to be the most difficult in games like Smash Bros, with near-limitless combinations.

[03:04](https://youtu.be/mQJEWMmZutA?t=184) Open-world games must be tough as well, since the player can go almost anywhere they want.

[03:12](https://youtu.be/mQJEWMmZutA?t=192) In situations like these, human testing alone would prove far too cumbersome, so we sometimes have the computer search out issues for us. With Smash Bros., we would occasionally run CPU battles all night long to find bugs. The more times you bug test your game, the better— so we'll do global playtests near a project's end.

[03:34](https://youtu.be/mQJEWMmZutA?t=214) Testers in Japan, North America, and Europe will pass save data back and forth to conduct bug testing on a worldwide scale.

[03:46](https://youtu.be/mQJEWMmZutA?t=226) However, the trickiest thing about bugs is that whenever you resolve one, you run the risk of introducing new bugs. That's how bugs work, so you can't avoid them all just by being careful. Issues will always come up, no matter what.

[04:02](https://youtu.be/mQJEWMmZutA?t=242) The goal is to find and fix them quickly— which is what bug testing teams all over the world are doing, even now.
