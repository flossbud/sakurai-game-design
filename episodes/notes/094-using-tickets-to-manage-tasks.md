# 094 · Using Tickets to Manage Tasks

**Category:** Programming & Tech · [Video](https://www.youtube.com/watch?v=7NpLxkkeh6Y) · [Transcript](../transcripts/094-using-tickets-to-manage-tasks.md)

## In one sentence
Turn every work task into a ticket with one owner, a status and a deadline, so everyone can see who is responsible for what and nothing slips through the cracks.

## Key ideas
- On a project almost every task becomes a "ticket": digital data managed through a server-based tool, not paper. Tickets pass from one team member to another, and whoever holds the ticket has to do the work, which makes responsibility obvious.
- Even one game character breaks into many tickets: writing the spec and documentation, making the model and rig, animating, programming, visual effects, sound effects, balancing. Each ticket is assigned to a leader or team member, so its status is easy to confirm and nothing slips through the cracks.
- Upstream and downstream jobs can share one ticket (the animator can't start until the model exists). When work runs late, the next person downstream sometimes starts early with what they have, but it's better not to line tasks up that directly when you can avoid it.
- Every ticket has a status (in progress, complete, on hold, rescinded, and so on), which makes progress easy to judge. Tickets usually carry a deadline that a leader or manager tracks, so they can head off delays before they happen.
- Bug testing runs on tickets too: a tester confirms a bug, writes the report inside the ticket, and the section leader routes it to the right people. If it reaches the wrong person or needs more eyes, anyone can reassign it.
- The name changes from tool to tool, but the point is to make work tasks visible. Sakurai says old projects had no such system; today nothing would get done without it.

## Do this
- Split each content piece (e.g., one character) into separate tickets per discipline: spec/doc, model and rig, animation, programming, VFX, SFX, balancing. Give each ticket exactly one assigned owner.
- Give every ticket a status field (in progress / complete / on hold / rescinded) and a deadline, and have a lead review the deadlines regularly so slips get caught early.
- Link dependent work (animation waits on the model) in a shared ticket, and schedule a buffer so downstream people aren't forced to start on half-finished upstream work.
- Run bug reports through the same system: the tester confirms the bug and writes it up in the ticket, a section leader routes it, and anyone can reassign it if it landed on the wrong person.

## Avoid
- Work that lives only in conversation or memory, with no owner or status. That's how tasks slip through the cracks.
- Chaining dependent tasks so tightly that downstream staff routinely have to start before their inputs are ready.

## Examples from the episode
- **A single game character (generic example):** spec, model/rig, animation, programming, VFX, SFX and balancing each become tickets passed from team to team.
- **Bug testing:** testers get assigned tickets, confirm the bug, write the report in the ticket and send it back for routing.
