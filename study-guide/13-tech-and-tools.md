# 13 · Tech, Tools and Production Pipelines

> Sakurai talks about tech as a director who tuned every parameter of several games himself and has lived with the results of good and bad tools, builds and hardware. His view is practical. Tools decide how many times a team can try something, and the number of tries decides the quality. So he wants tunable values outside the code and a loop that turns an edit into something playable in one press. He wants debug modes that set up any test in seconds, and file and bug systems where nothing gets lost. He also keeps reminding developers that computers surprise you: an optimization can make a game harder, a dev board can run at a different speed from the retail unit, and a TV can add enough lag to ruin a game's feel. Since no game of modern size can be bug-free, the job is to aim testing where bugs live, fix carefully and ship as if no patch will ever come. Get this wrong and the game's feel, fairness and stability depend on luck.

## The big ideas

**Code is the bones, parameters are the muscles.** "You could say the code is the bones, and the parameters are the muscles." ([46](../episodes/notes/046-making-your-game-easy-to-tune.md), ≈01:14) Every value that might be tuned lives outside the code, in a table planners can edit at any time, because balancing continues long after the programmer's part is done ([68](../episodes/notes/068-put-parameters-in-brackets.md)). Tuning is where you iterate most, so the edit-to-test loop should be one button, not ten minutes and a reboot as on the original Smash and Melee ([46](../episodes/notes/046-making-your-game-easy-to-tune.md)). Make each parameter's meaning unmistakable: his specs wrap every tunable in brackets, and "I established a rule that anything inside brackets is turned into a parameter." ([68](../episodes/notes/068-put-parameters-in-brackets.md), ≈03:22) State every speed and time in an explicit unit: frames, pixels per frame or real-world units ([84](../episodes/notes/084-units-of-speed.md), [76](../episodes/notes/076-learn-to-count-frames.md)).

**Computers surprise you, so verify on what players will actually use.** Meteos got harder when late optimization sped it up, because game speed was tied to processing speed. Mushiking's pet got hungry faster on the retail unit than on the dev board he tuned with. Ultimate's CPUs felt too hard at launch for reasons he still doesn't know ([141](../episodes/notes/141-unexpected-results.md), [92](../episodes/notes/092-sodatete-kouchuu-ouja-mushiking.md), [74](../episodes/notes/074-meteos.md)). Keep game speed independent of the frame rate ([5](../episodes/notes/005-frame-rates.md)), verify the final build on retail hardware, and remove display lag from every test setup, because "many people don't recognize lag when they see it." ([8](../episodes/notes/008-down-with-lag.md), ≈01:19)

**Budget for the worst case, and spend where the eyes are.** For Smash on 3DS: "I considered 60 FPS gameplay to be an absolute must, so we pared things down until that was realized." ([135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), ≈08:33) Ultimate's stages had to hold 60 fps with eight fighters on screen ([99](../episodes/notes/099-an-up-close-look-at-smash-bros-stages.md)). Hardware is weaker than people think, so put detail where the camera looks and cut what nobody sees ([44](../episodes/notes/044-distinguishing-between-major-and-minor-elements.md)). Tight limits are design fuel: Kirby's Dream Land shared and mirrored art to fit 64 KB and faked terrain collision with hand-authored paths ([100](../episodes/notes/100-development-secrets-of-the-original-kirby.md)).

**Bugs are combinatorial, so test smart, fix carefully and ship ready.** 89 fighters make about 8,000 pairings before anything else multiplies in, so brute force is impossible; aim at the places where systems fight over control ([136](../episodes/notes/136-bug-testing-never-ends.md)). Run bugs through tickets with repro steps, severity classes and the right owner ([208](../episodes/notes/208-bug-testing-systems.md)). Every fix can create a new bug ([208](../episodes/notes/208-bug-testing-systems.md)), and "no matter how much you improve your game through patches, it won't mean anything if your players have already given up on the game." ([231](../episodes/notes/231-online-updates.md), ≈03:31) Debug tools multiply all of this: "the convenience a debug mode provides will have a huge impact on a team's productivity." ([195](../episodes/notes/195-debug-mode.md), ≈02:09)

**Where episodes pull in different directions:**

- *60 fps vs. 30 fps.* Episode 5 calls 60 ideal but 30 still more than adequate, since 60 costs about half the visual budget. Episode 135 treats a stable 60 as non-negotiable for Smash. Pick per game: where timing and responsiveness are the fun (action, fighting), protect 60; where visuals carry the experience, 30 can be the right trade ([5](../episodes/notes/005-frame-rates.md), [135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md)).
- *The director's hands on the numbers.* Sakurai entered every parameter himself on early Smash games, Meteos and Kid Icarus: Uprising, then concluded that, with all his other duties, he should never have been the one entering them ([135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), [220](../episodes/notes/220-play-testing-keeps-going.md), [46](../episodes/notes/046-making-your-game-easy-to-tune.md)). The lesson isn't that directors shouldn't care about tuning. It's that the pipeline should let planners tune while the director supervises and protects identity.
- *Bug-free vs. ship-ready.* Demanding a bug-free game would make releasing games practically impossible ([136](../episodes/notes/136-bug-testing-never-ends.md)), yet patches can't win back players who already left ([231](../episodes/notes/231-online-updates.md)). Both hold: accept that bugs will ship, but set launch quality as if no patch is coming, and treat updates as a bonus.
- *Memory vs. processing.* Hand-authored animation and movement patterns cost ROM but save CPU; sharing and flipping art saves ROM ([100](../episodes/notes/100-development-secrets-of-the-original-kirby.md), [244](../episodes/notes/244-the-limitations-of-particle-effects.md)). Decide which resource is scarce, then trade the other for it.
- *Playful details vs. cutting the unseen.* He allows artists' playful touches when deadlines and performance aren't hurt, but toned down backdrop car tires that turned where nobody would see them ([44](../episodes/notes/044-distinguishing-between-major-and-minor-elements.md)).
- *Debug views as player features.* The trajectory guide moved from debug mode into Training Mode, though he worried it revealed too much. Ship such views only when they are easy to understand ([195](../episodes/notes/195-debug-mode.md)).
- *Demo or no demo.* Being known beats being unknown, but a half-baked demo can get a game written off and costs a second build's worth of QA ([122](../episodes/notes/122-game-demos.md)).

## Principles

### TECH-01 · Keep every tunable number out of the code
**Why:** If values are hard-coded, every tweak has to go through a programmer, yet balance keeps changing to the end. Parameters let the same code behave in drastically different ways. **Do:** Read every value that might be tuned from an external table that planners can edit. Express characters or vehicles as parameter sets on one shared behavior. Give a mode its own parameter set when its physics differ, and retune everything when the tempo changes. **Watch out:** Carrying old values into a game whose speed has changed.
*Sakurai's example:* Kirby Air Ride's machines all share one behavior and differ only by parameters, apart from star versus bike types ([59](../episodes/notes/059-kirby-air-ride.md)). Brawl's fighters needed a second jump and movement set for the Subspace Emissary ([108](../episodes/notes/108-super-smash-bros-brawl.md)). Ultimate's faster tempo meant none of Smash for's parameters could be reused ([160](../episodes/notes/160-super-smash-bros-ultimate.md)). · Episodes: [46](../episodes/notes/046-making-your-game-easy-to-tune.md), [68](../episodes/notes/068-put-parameters-in-brackets.md), [59](../episodes/notes/059-kirby-air-ride.md), [108](../episodes/notes/108-super-smash-bros-brawl.md), [135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), [160](../episodes/notes/160-super-smash-bros-ultimate.md)

### TECH-02 · Make the edit-and-test tuning loop a single button press
**Why:** Tuning is where you iterate most. Slow conversions discourage trying things and pile all the work onto one person. **Do:** Build a conversion tool, such as a spreadsheet add-in, that pushes parameters to every active dev kit in one press without a reboot. Give planners access so the director can supervise. **Watch out:** A director doing data entry on top of supervision, approvals and marketing.
*Sakurai's example:* Original Smash and Melee took ten minutes per conversion plus a reboot, with hand-edited text files. Bandai Namco Studios' Excel add-in updates all dev kits at once ([46](../episodes/notes/046-making-your-game-easy-to-tune.md)). From Smash for 3DS/Wii U a small planner team took over entry ([135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), [220](../episodes/notes/220-play-testing-keeps-going.md)). · Episodes: [46](../episodes/notes/046-making-your-game-easy-to-tune.md), [135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), [220](../episodes/notes/220-play-testing-keeps-going.md)

### TECH-03 · Make parameters unmistakable with plain-language names, units and formulas
**Why:** Several people tune parameters later, and terse names like "X-velocity" get misread. Specs don't work if you can't convey speed. **Do:** In specs, write each tunable as a bracketed plain-language phrase with O for the value, and keep a list pairing each phrase with its number. Put a unit on every speed and a frame count on every timing. Hide rarely used fields, and link dependent values with formulas, such as one move at half another's power. **Watch out:** Unitless numbers, and flat sheets where every field looks equally important.
*Sakurai's example:* "[Special startup X-velocity is O]" and "[Special X-deceleration is O/frame]" ([68](../episodes/notes/068-put-parameters-in-brackets.md)). Mario's top speed of about 1 pixel per frame on a 256-pixel-wide NES screen ([84](../episodes/notes/084-units-of-speed.md)). · Episodes: [68](../episodes/notes/068-put-parameters-in-brackets.md), [46](../episodes/notes/046-making-your-game-easy-to-tune.md), [84](../episodes/notes/084-units-of-speed.md), [76](../episodes/notes/076-learn-to-count-frames.md), [5](../episodes/notes/005-frame-rates.md)

### TECH-04 · Keep game speed independent of frame rate and processing speed
**Why:** Frames are a game's unit of time and distance equals time times speed, so whatever counts time controls everything. A dropped frame is not slowdown unless your logic makes it so. **Do:** Drive logic from a clock that doesn't depend on how many frames are drawn or how fast the CPU runs. Tell frame drops from true slowdown. Find any timing still tied to processing speed, and lock processing speed and frame timing before final balance. **Watch out:** Treating an optimization as purely good when it also changes game speed.
*Sakurai's example:* His NES and SNES games counted screen interrupts, so the 50 fps PAL versions ran at 5/6 speed ([5](../episodes/notes/005-frame-rates.md)). Meteos became harder after late optimization ([141](../episodes/notes/141-unexpected-results.md), [74](../episodes/notes/074-meteos.md)). · Episodes: [5](../episodes/notes/005-frame-rates.md), [141](../episodes/notes/141-unexpected-results.md), [74](../episodes/notes/074-meteos.md), [92](../episodes/notes/092-sodatete-kouchuu-ouja-mushiking.md)

### TECH-05 · Set the frame-rate target early and cut content until it holds
**Why:** 60 and 30 fps differ in both look and control, and a port can keep every enemy in place yet lose its mood if it runs choppy. **Do:** Choose the target per game at the start. Budget for the heaviest scene, let the weakest platform set shared limits, and cut or simplify features before lowering the target. **Watch out:** Budgeting from typical scenes, then dropping the target late.
*Sakurai's example:* Smash for 3DS ran four players, stereoscopic 3D, items, Pokémon and Assist Trophies at a stable 60, while Ice Climbers were too much for the 3DS ([135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md)). The NES Ghosts 'n Goblins lost its smoothness and creepiness to a low frame rate ([156](../episodes/notes/156-special-crossover-2.md)). · Episodes: [5](../episodes/notes/005-frame-rates.md), [135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), [99](../episodes/notes/099-an-up-close-look-at-smash-bros-stages.md), [156](../episodes/notes/156-special-crossover-2.md), [125](../episodes/notes/125-kid-icarus-uprising.md)

### TECH-06 · Spend processing where players look, and cut what nobody sees
**Why:** Console hardware is weaker than people think, and the less you process each object, the more you can show. **Do:** Spend detail on the screen center, the area in front of the camera and playable surfaces. Size model budgets by on-screen size (raised for close-up use elsewhere), and build LOD only when the gain justifies the labor. Lock finger joints and swap preset poses. Use billboards for flashes and simple objects, and keep particles short-lived, fast, packed and staggered. **Watch out:** Detail nobody will see, and billboards the camera can circle.
*Sakurai's example:* Smash skyspheres detailed only in front of the camera; Inkling's stage backdrop tires toned down ([44](../episodes/notes/044-distinguishing-between-major-and-minor-elements.md)). The N64 Smash fighter was about 300 polygons, about 200 with three or more fighters ([40](../episodes/notes/040-super-smash-bros-melee.md)). · Episodes: [44](../episodes/notes/044-distinguishing-between-major-and-minor-elements.md), [10](../episodes/notes/010-draw-the-light-not-the-asset.md), [210](../episodes/notes/210-portraying-fingers.md), [244](../episodes/notes/244-the-limitations-of-particle-effects.md), [153](../episodes/notes/153-billboards.md), [40](../episodes/notes/040-super-smash-bros-melee.md)

### TECH-07 · Turn hard memory and processing limits into design tricks
**Why:** Limits reward technique: Super Mario Bros. held far more game than Mario Bros. in 40 KB against 24 KB. **Do:** Decide which resource is scarce. If it's memory, share and flip art, cap animation frames, stack bitplanes and compress runs. If it's processing, trade memory for it with hand-authored paths or frame animations. Test compression early on capped media before cutting content. **Watch out:** Asking for more resources before trying technique.
*Sakurai's example:* Kirby's Dream Land, designed mostly for 64 KB: Waddle Dee and Waddle Doo share a back half, Gordo is one flipped image, and Coner and Cappy follow hand-placed paths with no terrain collision ([100](../episodes/notes/100-development-secrets-of-the-original-kirby.md)). Ultimate's music fit in a quarter of Smash for's space on a cartridge capped at about 16 GB ([160](../episodes/notes/160-super-smash-bros-ultimate.md)). · Episodes: [100](../episodes/notes/100-development-secrets-of-the-original-kirby.md), [96](../episodes/notes/096-the-family-computer-and-the-nes.md), [118](../episodes/notes/118-family-basic.md), [183](../episodes/notes/183-long-ago-numbers-were-used-to-draw-pixel-art.md), [244](../episodes/notes/244-the-limitations-of-particle-effects.md), [160](../episodes/notes/160-super-smash-bros-ultimate.md)

### TECH-08 · Verify the final build on real retail hardware before sign-off
**Why:** Dev boards and production units can differ. "But when you're working with computers, sometimes there's no telling what you might get." ([141](../episodes/notes/141-unexpected-results.md), ≈03:13) **Do:** Play the finished game on retail units. Compare timer rates, time limits and enemy speeds with design values, and schedule a difficulty pass after late optimization. Treat several independent reports of the same feel problem as real. **Watch out:** Tuning only on dev hardware.
*Sakurai's example:* He tuned Mushiking on a custom dev board just under one square meter and never played the handheld. The pet gets hungry faster than planned, which puts constant stress on players ([92](../episodes/notes/092-sodatete-kouchuu-ouja-mushiking.md), [141](../episodes/notes/141-unexpected-results.md)). · Episodes: [141](../episodes/notes/141-unexpected-results.md), [92](../episodes/notes/092-sodatete-kouchuu-ouja-mushiking.md), [74](../episodes/notes/074-meteos.md)

### TECH-09 · Remove input and display lag from every test, demo and capture setup
**Why:** Lag ruins good response, and most people don't notice it. At 60 fps, every 16.67 ms of display latency is a frame. Lag also changes how heavy buttons feel, so it misleads tuning. **Do:** Before every session, press jump in an instantly responsive 2D game on that exact setup. Use Game Mode or Low Latency Mode, or turn off all picture processing. Check audio separately, and rule out display lag before retuning feel. **Watch out:** Trusting that someone else already checked.
*Sakurai's example:* The E3 2018 Treehouse: Live setup's lag ruined Smash Ultimate's controls until he pointed it out ([8](../episodes/notes/008-down-with-lag.md)). Mid-session, he swapped to his low-lag recording monitor ([156](../episodes/notes/156-special-crossover-2.md)). · Episodes: [8](../episodes/notes/008-down-with-lag.md), [156](../episodes/notes/156-special-crossover-2.md), [252](../episodes/notes/252-crt-displays.md), [19](../episodes/notes/019-giving-weight-to-buttons.md)

### TECH-10 · Calibrate for every controller, platform and regional hardware variant
**Why:** Sticks differ by console, a D-pad only gives 0 or 1, platforms put confirm and cancel in different places, and regional hardware can lack features. **Do:** Set the stick dead zone per platform, expose sensitivity for gesture inputs like flicks, list each target's audio, input and button conventions, and provide fallbacks. Count the processing cost of optional peripherals. **Watch out:** One sensitivity value for every console.
*Sakurai's example:* The NES lacked expansion-audio pins, so several games' music sounded different abroad ([239](../episodes/notes/239-famicom-and-nes-audio.md)). A 3DS twin-stick peripheral added about 5% processor load to a game already at the hardware's limit, so it couldn't be fully supported ([125](../episodes/notes/125-kid-icarus-uprising.md)). · Episodes: [19](../episodes/notes/019-giving-weight-to-buttons.md), [154](../episodes/notes/154-flick-input.md), [175](../episodes/notes/175-its-easier-if-they-already-know.md), [239](../episodes/notes/239-famicom-and-nes-audio.md), [197](../episodes/notes/197-button-settings.md), [84](../episodes/notes/084-units-of-speed.md), [125](../episodes/notes/125-kid-icarus-uprising.md)

### TECH-11 · Build debug commands for the test setups you use most
**Why:** Without them the team invents workarounds, and the debug mode is used every day. **Do:** Add direct commands for frequent setups on button combinations of the normal controller. Include capture tools (pause, rotate characters, zoom, change angle). Prune the menu regularly and strip it from release. **Watch out:** A separate debug controller that has to be hunted down, and a bloated menu.
*Sakurai's example:* Before Smash could set damage directly, the team made Fox's forward tilt deal 100% damage to set up tests ([195](../episodes/notes/195-debug-mode.md)). · Episodes: [195](../episodes/notes/195-debug-mode.md)

### TECH-12 · Add view toggles that isolate exactly what you are checking
**Why:** Capes hide poses, effects pass in an instant, and terrain must stand apart from backdrop. He calls per-element display toggles another must-have ([217](../episodes/notes/217-transparency-features.md)). **Do:** Add per-part or whole-model translucency and hiding, an on/off toggle for each display element, a collision highlight, and slow-motion and background-off views. Let outside reviewers use them. **Watch out:** Scaling or deleting model parts just to inspect an animation.
*Sakurai's example:* Smash Ultimate's caped fighters checked with transparency, which took little time to implement ([217](../episodes/notes/217-transparency-features.md)); collision surfaces shown in red ([30](../episodes/notes/030-emphasize-objects-with-collision.md)); effects recorded slowed with backgrounds off ([79](../episodes/notes/079-visual-effects-in-slow-motion.md)). · Episodes: [217](../episodes/notes/217-transparency-features.md), [30](../episodes/notes/030-emphasize-objects-with-collision.md), [79](../episodes/notes/079-visual-effects-in-slow-motion.md)

### TECH-13 · Reuse debug tools for footage, screenshots and player-facing aids
**Why:** Replay and debug cameras let a team find the best angle after the fact, and some debug views teach players. **Do:** Build replay with a free camera for trailers and screenshots. Promote easy-to-understand overlays into a training mode. **Watch out:** Overlays that reveal more about the systems than you want players to see.
*Sakurai's example:* Smash reveal gameplay shot with debug and replay features ([163](../episodes/notes/163-fighter-reveal-videos.md)); the Training Mode trajectory guide began as a debug feature he requested ([195](../episodes/notes/195-debug-mode.md)). · Episodes: [163](../episodes/notes/163-fighter-reveal-videos.md), [195](../episodes/notes/195-debug-mode.md), [50](../episodes/notes/050-jobs-in-game-development.md)

### TECH-14 · Aim testing at the places where systems fight over control
**Why:** Full coverage is impossible. A game of dozens of hours might need thousands to tens of thousands of hours to test fully, and bugs cluster where one system seizes another. **Do:** Estimate the test matrix early. Test first: grabs and throws (especially on a target mid special move), scene-changing supers, extreme or V-shaped terrain, growth and parameter systems, and conflicting AI modes. Run CPU-versus-CPU matches overnight and pass save data between regions near the end. **Watch out:** Random free play standing in for a test plan.
*Sakurai's example:* Ultimate's 89 fighters give about 8,000 pairings before moves, items, players, stages and spirits multiply in ([136](../episodes/notes/136-bug-testing-never-ends.md)). · Episodes: [136](../episodes/notes/136-bug-testing-never-ends.md), [208](../episodes/notes/208-bug-testing-systems.md), [221](../episodes/notes/221-computer-controlled-players.md), [231](../episodes/notes/231-online-updates.md)

### TECH-15 · Run bugs through tickets with repro steps, severity and the right owner
**Why:** Programmers make poor full-time testers, bugs on old builds mislead, and untracked work slips through the cracks. **Do:** Test only on the latest daily build, from design docs and checklists. File a ticket once the bug can be reproduced. Class S means hangs or possible save corruption, Class A means progression blockers, and lower classes may be waived. Route each ticket to the owning discipline, verify fixes in several configurations, and mark tickets resolved instead of deleting them. **Watch out:** Assuming programmers are always the right fixers: artists fix character problems and animators fix animations.
*Sakurai's example:* Smash's bug process ([208](../episodes/notes/208-bug-testing-systems.md)); one character split into spec, model and rig, animation, programming, VFX, SFX and balancing tickets ([94](../episodes/notes/094-using-tickets-to-manage-tasks.md)). · Episodes: [208](../episodes/notes/208-bug-testing-systems.md), [94](../episodes/notes/094-using-tickets-to-manage-tasks.md), [50](../episodes/notes/050-jobs-in-game-development.md)

### TECH-16 · Regression-test every fix, and keep late fixes narrow
**Why:** Fixing one bug can create others, "enbugging", so even urgent fixes can't ship at once. **Do:** Pair each fix with a regression pass before patching. Late in a project, prefer contained changes over core rewrites. **Watch out:** Hotfixes rushed out unchecked.
*Sakurai's example:* For Ultimate's too-hard launch CPUs, the patch lowered Challenger fight difficulty and added Very Easy to World of Light rather than touching core CPU functions ([141](../episodes/notes/141-unexpected-results.md)). · Episodes: [136](../episodes/notes/136-bug-testing-never-ends.md), [141](../episodes/notes/141-unexpected-results.md), [208](../episodes/notes/208-bug-testing-systems.md), [231](../episodes/notes/231-online-updates.md)

### TECH-17 · Ship as if no patch will come; treat updates as a bonus
**Why:** Modern games can't be perfect, developers barely get to play the final build, and the market finds the one-in-a-thousand bug. But patches can't recover players who already quit. **Do:** Set launch quality as if no update will ship, and lock content early enough to play near-final builds. After launch, crash fixes are a must, while balance and quality-of-life changes are optional. Watch player videos as your biggest test pass. **Watch out:** Treating updates and DLC as free; they stretch the schedule.
*Sakurai's example:* Smash for 3DS/Wii U released in fall to winter 2014, but development only wrapped in spring 2016 ([135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md)). · Episodes: [231](../episodes/notes/231-online-updates.md), [136](../episodes/notes/136-bug-testing-never-ends.md), [135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md), [141](../episodes/notes/141-unexpected-results.md)

### TECH-18 · Fix the code before you tune the numbers
**Why:** If the code has mistakes, almost no amount of adjustment gets the result you want, and the tuner's time is wasted. **Do:** When tuning stops responding predictably, stop and have strong programmers hunt the bug. Verify each move by feel against its spec. **Watch out:** Turning knobs on broken code.
*Sakurai's example:* In Melee's final stretch, Satoru Iwata debugged alongside the programmers; Sakurai doubts the game would otherwise have shipped before the end of 2001 ([259](../episodes/notes/259-mr-iwata.md)). · Episodes: [259](../episodes/notes/259-mr-iwata.md), [76](../episodes/notes/076-learn-to-count-frames.md)

### TECH-19 · Name files so they sort sensibly and read at a glance
**Why:** Category-first names group and order themselves, while direction-first names turn into a mess when sorted ([22](../episodes/notes/022-name-files-logically.md)). Others, including overseas teams, must understand them too. **Do:** Order names category, then modifiers, then numbers. Sort-test your folders, use English, and use one ID scheme everywhere. **Watch out:** Cryptic abbreviations and romanized native-language words.
*Sakurai's example:* Attack11 to Attack13, AttackS4, AttackAirF and SpecialHi, with N, Hi, S and Lw for directions ([22](../episodes/notes/022-name-files-logically.md)). · Episodes: [22](../episodes/notes/022-name-files-logically.md), [261](../episodes/notes/261-masahiro-sakurai-on-creating-games-finale-special.md)

### TECH-20 · Keep every file on a server with locking, merging and history
**Why:** Big games have tens of thousands to millions of files and possibly hundreds of editors. Locks alone are inefficient for huge files, and reversions happen often. **Do:** Lock to edit and upload to unlock. Allow concurrent edits with merging on large shared files, with a named person resolving leftovers, and recover lost work from version history. **Watch out:** Believing the tool makes lost work impossible. "There shouldn't be any issues, in theory— but in practice, it's a constant source of headaches." ([172](../episodes/notes/172-how-multiple-people-work-on-one-file.md), ≈02:10)
*Sakurai's example:* A general overview with no game-specific example ([172](../episodes/notes/172-how-multiple-people-work-on-one-file.md)). · Episodes: [172](../episodes/notes/172-how-multiple-people-work-on-one-file.md)

### TECH-21 · Treat a pre-release demo as a second build with its own QA
**Why:** Spoiler data will be found, removing data breaks things, and a public build needs nearly full testing. **Do:** Schedule the demo as its own deliverable, keep spoilers in separable files, audit, retest, and release only once it's balanced. **Watch out:** Treating it as a quick slice of the full game.
*Sakurai's example:* General guidance ([122](../episodes/notes/122-game-demos.md)). · Episodes: [122](../episodes/notes/122-game-demos.md)

### TECH-22 · Build CPU players from data and give them human reflexes
**Why:** The computer has no eyes, superhuman reactions feel extremely unfair, and layered logic contradicts itself. **Do:** Give the AI queryable reach, timing and movement data plus the opponent's attack data, position and status. Add a reaction delay, test mode conflicts, and tune high levels toward offense. **Watch out:** Perfect defense, which could be invincible but no fun.
*Sakurai's example:* Ultimate's CPUs have a "reflex" delay and were tuned for offense ([221](../episodes/notes/221-computer-controlled-players.md)). · Episodes: [221](../episodes/notes/221-computer-controlled-players.md), [141](../episodes/notes/141-unexpected-results.md)

### TECH-23 · Seed randomness with an unpredictable value
**Why:** Computers can't make true randomness, so players reset to force results. **Do:** Factor the internal clock or another indefinite value into the seed. **Watch out:** Fixed seeds after a reset.
*Sakurai's example:* A caution from his randomness episode ([189](../episodes/notes/189-randomness-spices-games-up.md)). · Episodes: [189](../episodes/notes/189-randomness-spices-games-up.md)

### TECH-24 · Match real-time online players within their local region
**Why:** Fully synchronous play like Smash suffers from lag far more than asynchronous play like Mario Kart. **Do:** Match within the local region, not just the country, and tune match range against population. **Watch out:** A range so narrow nobody finds a match, or so wide that matches are lopsided ([170](../episodes/notes/170-the-pros-and-cons-of-leaderboards.md)).
*Sakurai's example:* Brawl's online play ([108](../episodes/notes/108-super-smash-bros-brawl.md)). · Episodes: [108](../episodes/notes/108-super-smash-bros-brawl.md), [170](../episodes/notes/170-the-pros-and-cons-of-leaderboards.md)

### TECH-25 · Keep reference hardware, cables and displays organized and calibrated
**Why:** Old games stay working tools, and monitors that disagree on color are fatal for art checks. **Do:** Use a selector for reference consoles, label every cable and adapter, give each console a switchable outlet and ventilation, and calibrate monitors by eye against one shared reference screen under neutral light. **Watch out:** Tinted office light that skews the art.
*Sakurai's example:* His six-door game cabinet with Tepra labels ([216](../episodes/notes/216-storage-tips.md)); an office lit yellow whose art came out bluish ([184](../episodes/notes/184-dealing-with-color-disparity.md)). · Episodes: [216](../episodes/notes/216-storage-tips.md), [184](../episodes/notes/184-dealing-with-color-disparity.md), [8](../episodes/notes/008-down-with-lag.md)

## Common mistakes

- Hard-coding tunable values, or letting one person be the only one who can change them ([46](../episodes/notes/046-making-your-game-easy-to-tune.md), [68](../episodes/notes/068-put-parameters-in-brackets.md)).
- A tuning loop of minutes and reboots instead of one button ([46](../episodes/notes/046-making-your-game-easy-to-tune.md)).
- Parameters without units or with names only their author understands ([68](../episodes/notes/068-put-parameters-in-brackets.md), [84](../episodes/notes/084-units-of-speed.md)).
- Game logic tied to frame rate or processing speed, then optimizing late ([5](../episodes/notes/005-frame-rates.md), [141](../episodes/notes/141-unexpected-results.md)).
- Tuning only on a dev board and never playing the retail unit ([92](../episodes/notes/092-sodatete-kouchuu-ouja-mushiking.md)).
- Demoing or playtesting on displays with picture processing switched on ([8](../episodes/notes/008-down-with-lag.md)).
- Budgeting performance for the average scene instead of the worst ([99](../episodes/notes/099-an-up-close-look-at-smash-bros-stages.md), [135](../episodes/notes/135-super-smash-bros-for-3ds-wii-u.md)).
- Spending detail where nobody looks, and building LOD by reflex ([44](../episodes/notes/044-distinguishing-between-major-and-minor-elements.md)).
- Workarounds instead of debug commands, a separate debug controller, and a bloated debug menu ([195](../episodes/notes/195-debug-mode.md)).
- Editing models just to see an animation ([217](../episodes/notes/217-transparency-features.md)).
- Free-play "testing" with no plan or priorities ([136](../episodes/notes/136-bug-testing-never-ends.md), [208](../episodes/notes/208-bug-testing-systems.md)).
- Bug reports from old builds, without repro steps, or deleted once fixed ([208](../episodes/notes/208-bug-testing-systems.md)).
- Hotfixes shipped without regression checks ([136](../episodes/notes/136-bug-testing-never-ends.md)).
- Shipping rough on the promise of a patch ([231](../episodes/notes/231-online-updates.md)).
- Tuning on top of buggy code ([259](../episodes/notes/259-mr-iwata.md)).
- Direction-first or romanized file names, and files passed around by hand ([22](../episodes/notes/022-name-files-logically.md), [172](../episodes/notes/172-how-multiple-people-work-on-one-file.md)).
- Leaving spoiler data in a demo ([122](../episodes/notes/122-game-demos.md)).

## Review questions

1. How long does one tuning change take to reach a playable build, and who on the team can make it?
2. Does the game run at the same speed and difficulty at any frame rate, on any machine and in any region?
3. Does the heaviest scene hold the frame-rate target on the weakest platform?
4. Was this build's feel judged on a verified lag-free display chain?
5. Can the team set up any test situation in seconds and see exactly what they're checking?
6. Where do systems fight over control in this build, and were those tested first?
7. Is every bug a ticket with repro steps, a class, an owner and a verified fix?
8. If no patch ever shipped, would this build be acceptable on day one?
9. Could a newcomer find, read and safely edit any file in the project?

## Exercises

1. **Magic-number hunt.** Search the codebase for numeric literals in gameplay code. Move the ten most-tuned into a parameter table with plain-language names and units. Time the loop from edit to playable before and after, and try to get it under a few seconds ([46](../episodes/notes/046-making-your-game-easy-to-tune.md), [68](../episodes/notes/068-put-parameters-in-brackets.md)).
2. **Half-speed test.** Cap the frame rate at half its target (or slow the CPU) and replay one timed challenge. If anything moves slower, gets easier or harder, or a timer drifts, decouple it ([5](../episodes/notes/005-frame-rates.md), [141](../episodes/notes/141-unexpected-results.md)).
3. **Lag audit.** Take every display your team tests or demos on, set each to Game Mode, and do the jump test. Write the setting checklist on a card taped to each screen ([8](../episodes/notes/008-down-with-lag.md)).
4. **Debug wish list.** Ask each discipline which test setup it rebuilds by hand most often. Build the top three as debug commands on the normal controller, plus a per-element display toggle and a transparency toggle ([195](../episodes/notes/195-debug-mode.md), [217](../episodes/notes/217-transparency-features.md)).
5. **Hot-spot test pass.** List every place one entity takes control of another (grabs, carries, cutscene captures, mounts, possessions) and every scene change. Spend one session testing only those, each against targets in unusual states ([136](../episodes/notes/136-bug-testing-never-ends.md)).
6. **Bug triage drill.** Take your open bug list and give each bug a reproduction step, a severity class (S: hang or save corruption; A: blocks progress; lower) and an owner by discipline. Close nothing without a tester's verification ([208](../episodes/notes/208-bug-testing-systems.md)).
